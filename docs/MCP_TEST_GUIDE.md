# MCP 工具调用评测指南

## 一、测试目标

验证你的项目是否真正接入了 MCP（Model Context Protocol）地图工具，并量化评估工具调用的准确性。

**面试价值**：
- 证明你不是"纸上谈兵"，真的接入了 MCP
- 展示对工具调用准确性的量化评估能力
- 体现工程化测试思维

---

## 二、测试原理

### 2.1 什么是 MCP 工具调用

MCP 是一种协议，允许 LLM 调用外部工具（如地图 API、数据库、文件系统等）。

在你的项目中：
- **MCP 服务**：高德地图 API（配置在 `mcp-servers.json`）
- **调用方式**：通过 `ToolCallbackProvider` 注入到 `ChatClient`
- **触发条件**：用户查询涉及地理位置、路线规划时，LLM 自动调用地图工具

### 2.2 如何判断工具被调用了

**方法 1：响应内容特征**
- 包含地图特征词：距离、公里、分钟、路线、导航等
- 包含具体数字+单位组合（如"15公里"、"30分钟"）

**方法 2：后端日志**
- 查看 `MyLoggerAdvisor` 日志，是否有 tool execution 相关记录

### 2.3 测试用例设计

我们设计了 **7 条测试用例**：

| 类型 | 数量 | 说明 |
|------|------|------|
| 需要调用 MCP | 5 条 | 路线规划、距离查询、综合查询等 |
| 不需要调用 MCP | 2 条 | 纯 RAG 查询（对照组） |

**为什么要有对照组？**
- 验证系统不会"过度调用"工具
- 确保 RAG 查询不会误触发地图工具

## 四、结果解读

### 4.1 关键指标

| 指标 | 说明 | 目标值 |
|------|------|--------|
| **成功率** | 整体测试通过率 | ≥ 70% |
| **工具调用正确率** | 该调用时调用，不该调用时不调用 | ≥ 90% |
| **平均延迟** | 单次请求平均耗时 | < 8000ms |

### 4.2 常见失败原因

1. **工具未调用（应该调用但没调用）**
   - 原因：查询描述不够明确，LLM 没有识别出需要地图工具
   - 解决：优化 Prompt，增加地理位置关键词

2. **内容验证失败**
   - 原因：LLM 回答了，但没有包含预期的关键词
   - 解决：放宽验证条件，或检查 LLM 是否真的调用了工具

3. **延迟过高**
   - 原因：地图 API 响应慢，或 LLM 推理时间长
   - 解决：这是外部依赖问题，无法优化（可以在面试中说明）

## 六、常见追问及应对

### Q1：你怎么判断工具被调用了？

**答**：
我用了两种方法：
1. **内容特征检测**：检查响应中是否包含地图特征词（距离、公里、分钟等）
2. **日志验证**：查看后端日志，确认是否有 tool execution 记录

这两种方法结合，可以准确判断工具是否被调用。

### Q2：为什么要有对照组？

**答**：
对照组用来验证系统不会"过度调用"工具。比如用户问"住宿标准是多少"，这是纯 RAG 查询，不应该调用地图工具。如果对照组也触发了工具调用，说明系统判断逻辑有问题。

### Q3：工具调用失败了怎么办？

**答**：
失败原因主要有两类：
1. **查询不明确**：优化 Prompt，增加地理位置关键词
2. **任务太复杂**：引入 Agent 编排，将复杂任务拆解为多个子任务

在实际项目中，我会根据失败模式调整策略。

### Q4：这个测试有什么局限性？

**答**：
主要局限性是：
1. **测试用例有限**：只有 7 条，覆盖面不够广
2. **验证逻辑简单**：只检查关键词，没有深度语义分析
3. **依赖外部 API**：地图 API 不稳定会影响测试结果

但对于简历项目来说，这个测试已经足够证明我的工程化能力了。

## 七、下一步优化方向

1. **扩展测试用例**：增加到 20-30 条，覆盖更多场景
2. **引入语义相似度**：用 Embedding 模型计算响应与预期的相似度
3. **监控工具调用链路**：记录每次工具调用的参数、返回值、耗时
4. **A/B 测试**：对比不同 Prompt 策略的工具调用准确率
