# 重排序和三路召回测试指南

本测试用于评估重排序和三路召回的效果，包括：
- 多样化查询场景
- 性能指标统计
- 准确率评估

## 评估指标

### 1. 性能指标

| 指标 | 说明 | 目标值 |
|------|------|--------|
| **召回耗时** | 三路召回总耗时 | <300ms |
| **重排序耗时** | 重排序总耗时 | <200ms |
| **总耗时** | 端到端延迟 | <500ms |
| **召回数量** | 召回的文档数 | 10-30个 |
| **最终返回** | 重排后返回数 | 5个 |

### 2. 准确率指标（需人工评估）

对于每个查询，评估Top-5结果：

| 指标 | 计算方式 | 说明 |
|------|---------|------|
| **Precision@5** | 相关文档数 / 5 | Top-5中相关文档的比例 |
| **相关性评分** | 1-5分 | 1=不相关，5=完全相关 |
| **排序质量** | 好/中/差 | 最相关的文档是否排在前面 |

### 3. 对比分析

对比4种策略的效果：

| 策略 | 召回率 | 准确率 | 延迟 | 综合评分 |
|------|--------|--------|------|---------|
| 基础RAG | 低 | 中 | 快 | ⭐⭐⭐ |
| 查询重写+RAG | 中 | 中 | 中 | ⭐⭐⭐⭐ |
| 三路召回 | 高 | 高 | 中 | ⭐⭐⭐⭐⭐ |
| 三路召回+重排 | 高 | 很高 | 慢 | ⭐⭐⭐⭐⭐ |

## 问题排查

### 问题1：重排序耗时过长（>1000ms）

**可能原因**：
- DashScope API 网络延迟
- 批量编码文档数过多
- API限流

**解决方案**：
1. 检查网络连接
2. 减少 `MAX_RERANK_SIZE`（从30降到20）
3. 添加Query缓存

### 问题2：分数完全一致

**可能原因**：
- 测试数据单一
- 某个文档完全匹配查询

**解决方案**：
- 使用多样化查询（已修复）
- 检查文档内容是否重复

### 问题3：召回数量为0

**可能原因**：
- 向量库未初始化
- BM25索引未构建
- 查询改写失败

**解决方案**：
1. 检查向量库是否有数据
2. 检查BM25索引是否存在
3. 查看查询改写日志

## 下一步优化

### 短期（1周）

1. **添加Query缓存**
   - 缓存query embedding
   - 预期延迟降低22%

2. **减少重排数量**
   - MAX_RERANK_SIZE: 30 → 20
   - 预期延迟降低30%

3. **增加准确率评估**
   - 人工标注测试集
   - 计算Precision@5和NDCG@5

### 中期（1个月）

1. **异步预热**
   - 在召回阶段就开始计算query embedding
   - 预期延迟降低20%

2. **分层重排**
   - 粗排（规则）+ 精排（交叉编码）
   - 预期延迟降低40%

3. **智能路由**
   - 简单查询跳过重排序
   - 预期平均延迟降低50%
