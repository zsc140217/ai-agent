## 1. 测试相关追问

### ★ Q1.1：你的测试数据是怎么设计的？

**标准答案**：
> "我按三个维度设计了 25 条测试用例：
> 
> 1. **难度维度**：easy / medium / hard 三档
>    - Easy：直接查询（如"北京住宿标准"）
>    - Medium：需要理解同义词（如"去魔都出差"）
>    - Hard：需要多步推理或计算（如"住宿+伙食总费用"）
> 
> 2. **分类维度**：住宿费用 / 交通费用 / 补贴标准 / 客户信息 / 综合查询
> 
> 3. **城市维度**：一类城市 / 二类城市 / 通用场景
> 
> 每条用例都有明确的验证标准：必须包含的关键词、不能包含的错误信息。这样可以避免主观判断，保证测试的可复现性。"

**追问**：为什么只有 25 条，不是 100 条？
> "这是 MVP（最小可行产品）版本，目标是快速验证优化方向是否有效。25 条已经能覆盖主要场景，并且发现了明确的优化方向（多步计算问题）。我已经规划了扩展到 80-100 条的路线图，但先用小数据集快速迭代更符合敏捷开发理念。"

---

### ★ Q1.2：你怎么保证测试的客观性？

**标准答案**：
> "我用了三层验证逻辑：
> 
> 1. **必须包含预期答案**：如问"北京住宿标准"，响应必须包含"500"
> 2. **不能包含错误信息**：如不能包含"350"（二类城市标准）
> 3. **至少包含一个预期关键词**：如["500", "一类城市", "北京"]至少命中一个
> 
> 这样可以避免'看起来对但实际错'的情况。比如 LLM 回答很长，但没有直接给出关键数字，就会被判定为失败。
> 
> 另外，我还做了模糊匹配优化，比如'500元'、'500 元'、'每晚500元'都能识别为包含'500'，避免因格式问题误判。"

---

### ★ Q1.3：准确率从 40% 提升到 80%，这个提升是真实的吗？

**标准答案**：
> "是真实的，而且有明确的原因：
> 
> 1. **Baseline 40%**：直接问 LLM，不用知识库。LLM 只能靠训练数据猜，很多细节（如具体金额）会编造或答错。
> 
> 2. **Query Rewriting 60%**：先把'去魔都出差'改写成'上海市一类城市住宿标准'，让检索更精准。这一步就提升了 20%。
> 
> 3. **Full RAG 80%**：在查询重写基础上，加上向量检索和上下文注入。LLM 能看到准确的规章制度，准确率再提升 20%。
> 
> 这个提升是可复现的，我可以随时重新跑测试验证。而且失败的 5 个用例有明确的失败模式（多步计算），不是随机失败。"

**追问**：为什么 Full RAG 的延迟反而比 Query Rewriting 低？
> "因为检索更精准，减少了无效上下文的注入。Query Rewriting 虽然改写了查询，但如果检索结果还是不准，LLM 会收到很多无关信息，处理时间反而更长。Full RAG 通过向量检索找到最相关的文档，上下文更短更精准，所以延迟反而降低了。"

### Q1.4：你的测试覆盖率是多少？

**标准答案**：
> "如果按功能模块算：
> - 住宿费用查询：10/10 覆盖（一类、二类城市各 5 个）
> - 交通费用查询：3/3 覆盖（高铁、飞机、市内交通）
> - 补贴标准查询：3/3 覆盖（伙食、交通、条件判断）

>

## 2. 技术选型追问

### ★ Q2.1：为什么选 Spring AI 而不是 LangChain？

**标准答案**：
> "主要考虑三点：
> 
> 1. **生态匹配**：我们的技术栈是 Java + Spring Boot，Spring AI 是官方项目，与 Spring 生态无缝集成。LangChain 的 Python 版本更成熟，但 Java 版本（LangChain4j）文档较少，社区活跃度低。
> 
> 2. **企业级支持**：Spring AI 有 Spring 官方背书，长期维护有保障。对企业应用来说，稳定性比功能丰富度更重要。
> 
> 3. **学习深度**：自研 ReAct Agent 让我深入理解了 Agent 的工作原理，而不是只会调 API。这对技术成长更有价值。
> 
> 如果是 Python 项目，我会优先选 LangChain。技术选型要看具体场景，不是哪个更火就选哪个。"

---

### ★ Q2.2：为什么用内存向量库而不是 PgVector？

**标准答案**：
> "这是分阶段实施的策略：
> 
> 1. **MVP 阶段（当前）**：用 SimpleVectorStore（内存向量库）
>    - 优点：零依赖，启动快，适合本地开发和快速验证
>    - 缺点：数据不持久化，重启后需要重新加载
> 
> 2. **生产阶段（规划中）**：切换到 PgVector
>    - 优点：数据持久化，支持分布式部署，SQL 友好
>    - 缺点：需要部署 PostgreSQL，运维成本高
> 
> 我的测试重点是验证 RAG 策略是否有效，而不是测试数据库性能。用内存向量库可以排除数据库因素的干扰，更纯粹地测试 RAG 效果。
> 
> 下一步我会做'内存 vs PgVector'的横向对比测试，量化数据库带来的性能差异。"

---

### Q2.3：为什么选通义千问而不是 GPT-4？

**标准答案**：
> "主要考虑三点：
> 
> 1. **中文能力**：通义千问对中文的理解更好，尤其是企业规章制度这种正式文本。
> 
> 2. **成本**：通义千问的价格是 GPT-4 的 1/10 左右，对学生项目更友好。
> 
> 3. **合规性**：通义千问在国内合规，不需要翻墙，API 稳定性更好。
> 
> 如果是英文场景或对准确率要求极高的场景，我会选 GPT-4。但对这个项目来说，通义千问的性价比更高。"

## 3. RAG 优化追问

### ★ Q3.1：Query Rewriting 具体是怎么实现的？

**标准答案**：
> "我用的是 Spring AI 的 `QueryTransformer` 接口，核心逻辑是：
> 
> 1. **输入**：用户原始查询（如'去魔都出差住宿能报多少'）
> 
> 2. **重写规则**：
>    - 同义词替换：'魔都' → '上海'
>    - 补充上下文：'住宿' → '住宿费用报销标准'
>    - 结构化：'能报多少' → '报销上限金额'
> 
> 3. **输出**：结构化查询（如'上海市一类城市住宿费用报销标准上限金额'）
> 
> 实现方式有两种：
> - **基于规则**：维护一个同义词词典（如'魔都' → '上海'）
> - **基于 LLM**：让 LLM 改写查询（我用的这种，更灵活）
> 
> 代码在 `QueryRewriter.java`，核心就是调用 LLM 的 `transform()` 方法。"

**追问**：Query Rewriting 会不会改变用户意图？
> "有可能，但概率很低。我在 System Prompt 中明确要求'只改写表达方式,不改变原意'。而且我做了对比测试，Query Rewriting 使准确率从 40% 提升到 60%，说明改写是有效的，没有大规模误判。
> 
> 如果担心改变意图，可以加一个'改写确认'步骤，让用户确认改写后的查询是否正确。但这会影响用户体验，所以我没有加。"

---

### ★ Q3.2：你的 RAG 和普通的向量检索有什么区别？

**标准答案**：
> "主要有三个优化：
> 
> 1. **Query Rewriting（查询重写）**：
>    - 普通 RAG：直接用用户原始查询检索
>    - 我的优化：先改写成结构化查询，再检索
>    - 效果：准确率从 40% 提升到 60%
> 
> 2. **Metadata Enrichment（元数据增强）**：
>    - 普通 RAG：只存储文档内容
>    - 我的优化：给文档打标签（城市等级、费用类型等）
>    - 效果：可以按元数据过滤，提升检索精度
> 
> 3. **Token-based Splitting（基于 Token 的切分）**：
>    - 普通 RAG：按字符数切分（如每 500 字一段）
>    - 我的优化：按 Token 数切分，保证语义完整性
>    - 效果：避免把一句话切成两段
> 
> 这三个优化是渐进式的，每一步都有明确的提升效果。"

---

### Q3.3：你怎么评估 RAG 的检索质量？

**标准答案**：
> "我用了端到端的准确率评估，而不是单独评估检索层。原因是：
> 
> 1. **最终目标是答案正确**：检索结果再好，如果 LLM 没有正确理解，答案还是错的。
> 
> 2. **检索和生成是耦合的**：Query Rewriting 既影响检索，也影响生成。单独评估检索层无法反映整体效果。
> 
> 如果要单独评估检索层，可以用这些指标：
> - **Recall@K**：前 K 个结果中包含正确文档的比例
> - **MRR（Mean Reciprocal Rank）**：第一个正确文档的排名倒数
> - **NDCG**：考虑排序质量的指标
> 
> 但对这个项目来说，端到端准确率更直观，也更符合业务目标。"

## 4. Agent 架构追问

### ★ Q4.1：你的 ReAct Agent 和 LangChain 的 Agent 有什么区别？

**标准答案**：
> "核心思想一样（Reasoning + Acting），但实现细节不同：
> 
> 1. **状态管理**：
>    - LangChain：用 `AgentExecutor` 管理状态
>    - 我的实现：自定义 `AgentState` 类，更轻量
> 
> 2. **工具调用**：
>    - LangChain：通过 `@tool` 装饰器注册工具
>    - 我的实现：通过 `ToolRegistration` 类注册，更灵活
> 
> 3. **可控性**：
>    - LangChain：黑盒，难以调试
>    - 我的实现：每一步都可追溯，方便调试
> 
> 自研的好处是深入理解原理，坏处是功能没有 LangChain 丰富。但对学习和面试来说，自研更有说服力。"

---

### Q4.2：你的 Agent 最多支持多少步？为什么是 20 步？

**标准答案**：
> "最多支持 20 步，这是一个经验值：
> 
> 1. **实际测试**：我测试了 50 个任务，最复杂的任务用了 6 步，平均 3-4 步。20 步已经足够覆盖绝大多数场景。
> 
> 2. **防止死循环**：如果 Agent 陷入死循环（如反复调用同一个工具），20 步可以强制终止，避免无限循环。
> 
> 3. **成本控制**：每一步都要调用 LLM API，20 步已经是比较大的开销了。
> 
> 如果真的需要更多步骤，可以调整这个参数。但通常超过 10 步说明任务拆解有问题，应该优化任务设计而不是增加步数上限。"

---

### Q4.3：你的 Agent 如何避免幻觉？

**标准答案**：
> "我用了三层防护：
> 
> 1. **RAG 注入真实数据**：所有规章制度都从知识库检索，不让 LLM 凭空编造。
> 
> 2. **MCP 协议对接外部 API**：地理信息直接调用高德地图 API，不让 LLM 猜距离。
> 
> 3. **Structured Output**：要求 LLM 输出结构化数据（如 JSON），而不是自由文本。这样可以验证格式是否正确。
> 
> 但完全消除幻觉是不可能的，只能尽量降低。我的测试结果是 80% 准确率，说明还有 20% 的幻觉或错误。下一步优化方向是增加'答案验证'步骤，让 Agent 自己检查答案是否合理。"

## 6. 压力测试追问

### Q6.1：你的系统能支持多少并发？

**标准答案**：
> "我没有做严格的压测，因为这是单机部署的学习项目，不是生产系统。
> 
> 但根据测试数据推算：
> - 平均响应时间：7.5s
> - 单机 QPS：约 1-2（假设串行处理）
> - 如果用连接池并发处理，理论上可以支持 10-20 QPS
> 
> 主要瓶颈在 LLM API 调用（占 75% 延迟），不在我的代码。如果要提升并发，需要：
> 1. 使用异步调用（CompletableFuture）
> 2. 增加 LLM API 的并发配额
> 3. 引入缓存（相同问题直接返回缓存结果）
> 
> 但对学习项目来说，验证技术可行性比追求高并发更重要。"

---

### Q6.2：你的系统在生产环境会遇到什么问题？

**标准答案**：
> "主要有三个问题：
> 
> 1. **LLM API 稳定性**：
>    - 问题：API 可能超时、限流、返回错误
>    - 解决：增加重试机制、降级策略（API 失败时返回默认答案）
> 
> 2. **知识库更新**：
>    - 问题：规章制度更新后，向量库需要重新加载
>    - 解决：实现增量更新机制，不需要全量重建
> 
> 3. **成本控制**：
>    - 问题：每次调用 LLM API 都要花钱，高并发下成本很高
>    - 解决：增加缓存、Prompt 压缩、模型降级（简单问题用便宜模型）
> 
> 这些都是工程化的问题，不是技术难点。我的项目重点是验证 RAG 优化的有效性，生产化是下一步的工作。"

- Baseline 准确率：**40%**
