# 重排序性能测试分析报告

## 测试概述

**测试时间**: 2025-01-XX  
**测试方法**: `RetrievalStrategyComparisonTest.testPerformance()`  
**测试次数**: 100次  
**测试查询**: "杭州差旅报销标准是什么？"

## 问题诊断

### 1. 延迟超出预期

**预期**: 100ms  
**实际**: 650ms  
**差异**: 6.5倍

**原因分析**:
- DashScope API 网络延迟（批量编码14个文档需要500ms）
- 未实现Query缓存（每次都重新编码Query）
- 批量编码是串行调用，未并行化

### 2. 批量编码是主要瓶颈

**占比**: 77%（500ms / 650ms）

**原因**:
- 14个文档需要14次API调用（假设批量接口内部也是串行）
- 每个文档平均编码耗时：500ms / 14 ≈ 36ms
- 网络延迟 + 模型推理时间

### 3. 测试数据单一

**问题**: 100次测试都是同一个查询 "杭州差旅报销标准是什么？"

**影响**:
- 无法评估重排序对不同查询类型的效果
- 分数分布单一，无法验证准确率提升
- 无法发现边界情况（如否定查询、对比查询）

## 优化建议

### 短期优化（1周内）

#### 1. Query缓存
```java
private final Map<String, float[]> queryEmbeddingCache = new ConcurrentHashMap<>();

float[] queryEmbedding = queryEmbeddingCache.computeIfAbsent(query, 
    k -> embeddingModel.embed(k));
```

**预期收益**: 延迟降低 22%（650ms → 507ms）

#### 2. 减少重排数量
```java
private static final int MAX_RERANK_SIZE = 10; // 从14降到10
```

**预期收益**: 延迟降低 30%（650ms → 455ms）

#### 3. 增加测试多样性
```java
String[] queries = {
    "杭州差旅报销标准是什么？",           // 精确匹配
    "去上海出差能报销多少钱？",           // 口语化
    "一类城市住宿费用",                   // 关键词
    "拜访阿里巴巴客户需要准备什么？",     // 场景化
    "协议酒店价格",                       // 简短查询
    "北京住宿标准",                       // 地点查询
    "二类城市交通补贴",                   // 分类查询
    "不能住五星级酒店吗？",               // 否定查询
    "深圳和广州住宿标准对比",             // 对比查询
    "差旅报销需要哪些材料？"              // 流程查询
};
```

### 中期优化（1个月内）

#### 1. 异步预热
```java
@PostConstruct
public void warmUp() {
    CompletableFuture.runAsync(() -> {
        embeddingModel.embed("预热查询");
    });
}
```

**预期收益**: 首次查询延迟降低 20%（650ms → 520ms）

#### 2. 分层重排序
```java
// 第一层：快速粗排（BM25分数）
List<Document> topCandidates = documents.stream()
    .sorted(Comparator.comparing(doc -> doc.getMetadata("bm25_score")))
    .limit(10)
    .collect(Collectors.toList());

// 第二层：精细重排（交叉编码）
return rerank(query, topCandidates, 5);
```

**预期收益**: 延迟降低 40%（650ms → 390ms）

## 面试回答模板

### Q: 你们的重排序延迟是多少？

**A**: 
"我们的重排序平均延迟是650ms，其中Query编码140ms，批量编码500ms。相比基础RAG的235ms，完整流程延迟是885ms，性能差异约3.77倍。

我们已经识别出批量编码是主要瓶颈（占77%），计划通过Query缓存、减少重排数量、分层重排等方式优化到300ms以内。"

### Q: 重排序效果如何？

**A**:
"从测试数据看，重排序Top-3的分数分布是0.9999、0.8776、0.8738，说明模型能够有效区分文档相关性。

但目前测试数据单一（100次都是同一查询），无法全面评估准确率提升。我们计划增加10种查询类型（精确匹配、口语化、否定查询等），通过人工评估来量化准确率提升。"

### Q: 为什么不用专门的重排序模型？

**A**:
"我们选择用DashScope Embedding模拟交叉编码，主要考虑：
1. **成本**: 避免引入新模型的部署和维护成本
2. **延迟**: DashScope API延迟可控（650ms）
3. **效果**: 交叉编码方式（query+doc拼接）能够捕捉语义交互

如果未来对准确率要求更高，可以考虑部署专门的bge-reranker模型。"
