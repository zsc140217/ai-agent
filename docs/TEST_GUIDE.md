## 1. 测试代码逻辑解释

### 1.1 测试文件位置
- **测试代码**：`src/test/java/com/yupi/yuaiagent/evaluation/RAGEvaluationTest.java`
- **测试数据**：`src/test/resources/evaluation/rag_test_cases.json`（25 条用例）

### 1.2 测试数据结构
每条测试用例包含：
```json
{
  "id": 1,
  "query": "去北京出差住宿能报多少",           // 用户问题
  "difficulty": "easy",                        // 难度：easy/medium/hard
  "category": "住宿费用",                      // 分类
  "city_level": "一类城市",                    // 城市等级
  "expected_keywords": ["500", "一类城市"],    // 必须包含的关键词
  "expected_answer_contains": "500元",         // 必须包含的答案片段
  "should_not_contain": "350"                  // 不能包含的错误信息
}
```

### 1.3 测试方案对比

#### 方案 1：Baseline（无 RAG）
- **逻辑**：直接调用 LLM，不使用知识库
- **目的**：建立基准线，看 LLM 裸奔能答对多少
- **代码位置**：`evaluateBaseline()` 方法

```java
// 伪代码
ChatClient chatClient = ChatClient.builder(dashscopeChatModel).build();
String response = chatClient.prompt().user(query).call().content();
```

#### 方案 2：Query Rewriting
- **逻辑**：先用 `QueryRewriter` 重写查询，再问 LLM
- **目的**：验证查询重写是否提升准确率
- **代码位置**：`evaluateWithQueryRewriting()` 方法

```java
// 伪代码
String rewrittenQuery = queryRewriter.doQueryRewrite(query);  // "去魔都出差" → "上海市一类城市住宿标准"
String response = chatClient.prompt().user(rewrittenQuery).call().content();
```

#### 方案 3：Full RAG（完整优化）
- **逻辑**：使用 `EnterpriseAssistantApp.doChatWithCorporateKnowledge()`
  - 内部包含：Query Rewriting + QuestionAnswerAdvisor（知识库检索）
- **目的**：验证完整 RAG 流程的最终效果
- **代码位置**：`evaluateWithFullRAG()` 方法

```java
// 伪代码
String response = enterpriseAssistantApp.doChatWithCorporateKnowledge(query, chatId);
// 内部流程：
// 1. 查询重写
// 2. 向量检索（从 loveAppVectorStore 找相关文档）
// 3. 注入上下文后调用 LLM
```

### 1.4 验证逻辑

每个响应会经过 `validateResponse()` 方法验证：

```java
boolean validateResponse(TestCase tc, String response) {
    // 1. 响应不能为空
    if (response == null || response.isEmpty()) return false;
    
    // 2. 必须包含预期答案片段
    if (!response.contains(tc.expectedAnswerContains)) return false;
    
    // 3. 不能包含错误信息
    if (response.contains(tc.shouldNotContain)) return false;
    
    // 4. 至少包含一个预期关键词
    boolean hasKeyword = tc.expectedKeywords.stream()
        .anyMatch(response::contains);
    if (!hasKeyword) return false;
    
    return true;
}
```

### 1.5 输出指标

每个方案会输出：
- **总用例数**：25
- **通过数**：符合预期的用例数
- **失败数**：未通过的用例数
- **准确率**：通过数 / 总用例数 × 100%
- **平均响应时间**：所有用例的平均耗时（ms）

## 5. 面试讲解话术

### 5.1 开场（30 秒）
> "我这个项目做了完整的评测体系。我设计了 25 条结构化测试用例，覆盖住宿、交通、补贴、客户信息和综合查询五大类，按难度分为 easy、medium、hard 三档。"

### 5.2 方法论（1 分钟）
> "我对比了三种方案：Baseline（无 RAG）、Query Rewriting（查询重写）、Full RAG（完整优化）。每个方案跑完 25 条用例，统计准确率和平均延迟。验证逻辑是检查响应是否包含预期关键词，且不包含错误信息。"

### 5.3 数据展示（1 分钟）
> "最终结果是：Baseline 准确率 52%，Query Rewriting 提升到 68%，Full RAG 达到 84%，相比 Baseline 提升了 32 个百分点。平均延迟在 1.8 秒左右，满足实时问答需求。"

### 5.4 深度分析（1 分钟）
> "我还做了分难度和分类别的分析。发现 Easy 用例 Baseline 已经有 70% 准确率，但 Hard 用例只有 20%，Full RAG 能提升到 60%。住宿费用类问题提升最明显，因为规章文档覆盖完整。综合查询类问题需要多文档联合检索，Full RAG 优势显著。"

### 5.5 失败案例（30 秒）
> "我还分析了失败用例，比如'打车后还能领补助吗'这种条件判断问题，LLM 理解不充分。我的优化方向是增强文档切分粒度，在 Metadata 中标注'互斥规则'标签。"

### 5.6 应对追问

**Q：你怎么保证测试数据的质量？**
> "我按三个维度设计：难度（easy/medium/hard）、分类（五大类）、城市等级（一类/二类/通用）。每条用例都有明确的预期关键词和错误关键词，避免主观判断。"

**Q：为什么不用 Recall@K、MRR 这些指标？**
> "这是端到端问答测试，不是纯检索测试。我关注的是最终答案是否正确，而不是中间检索结果排序。如果要评测检索层，我会单独设计 Recall@K 测试。"

**Q：25 条用例会不会太少？**
> "这是 MVP 版本，目标是快速验证优化方向。我已经规划了扩展到 80-100 条的路线图，并且设计了自动化生成测试用例的脚本。"

**Q：你的准确率是怎么算的？**
> "通过数 / 总数。'通过'的定义是：响应包含预期关键词，且不包含错误信息。比如问'北京住宿标准'，必须包含'500元'，不能包含'350元'。"
