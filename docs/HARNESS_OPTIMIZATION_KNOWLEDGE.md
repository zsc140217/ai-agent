## 🎯 核心知识点总结

### 1. Git Hooks自动化工作流

#### 知识点
- **Git Hooks原理**: Git在特定事件（commit、push、merge等）前后触发的脚本
- **Hook类型**: 
  - `pre-commit` - 提交前执行，用于代码检查
  - `post-commit` - 提交后执行，用于通知反馈
  - `pre-push` - 推送前执行，用于完整验证
- **配置方式**: `.claude/hooks.json` (Claude Code框架) 或 `.git/hooks/` (原生Git)

#### 实践应用
```json
{
  "pre:commit:*": [
    {
      "name": "secret-scan",
      "command": "bash scripts/secret-scan.sh",
      "description": "扫描敏感信息泄露"
    }
  ]
}
```

#### 面试回答模板
> "我在项目中配置了三层Git Hooks自动化：
> 1. **Pre-commit阶段** - 运行敏感信息扫描和快速测试（30秒内），拦截不合规提交
> 2. **Pre-push阶段** - 运行完整测试套件（2-3分钟），确保推送代码质量
> 3. **Post-commit阶段** - 提供即时反馈，提升开发体验
> 
> 这套机制在开发过程中拦截了X次潜在的密钥泄露，避免了Y次破坏性提交，显著提升了代码安全性。"

---

### 2. 敏感信息泄露防护

#### 知识点
- **常见泄露场景**: API密钥、数据库密码、Token硬编码到代码中
- **检测方法**: 正则表达式匹配关键词（api-key, secret, password, token）
- **Git暂存区扫描**: `git diff --cached` 检查即将提交的内容
- **防护策略**: 
  - 使用环境变量存储敏感信息
  - `.gitignore` 排除配置文件
  - Pre-commit hook自动拦截

#### 实践应用
```bash
# 检测API密钥泄露
if git diff --cached | grep -iE "(api[_-]?key|secret|password)" | grep -v "YOUR_"; then
    echo "❌ 检测到可能的API密钥泄露！"
    exit 1
fi
```

#### 面试回答模板
> "我实现了一套敏感信息泄露防护机制：
> 1. **Pre-commit扫描** - 使用正则表达式检测暂存区中的API密钥、密码等敏感信息
> 2. **白名单机制** - 允许占位符（如YOUR_API_KEY）通过，避免误报
> 3. **特定文件检查** - 针对application.yml等配置文件进行深度扫描
> 
> 这套机制的核心价值在于**预防而非补救** - 一旦敏感信息进入Git历史，即使删除也会永久留存。通过Pre-commit拦截，从源头杜绝泄露风险。"

### 3. 代码覆盖率与质量门禁

#### 知识点
- **代码覆盖率指标**:
  - 行覆盖率 (Line Coverage)
  - 分支覆盖率 (Branch Coverage)
  - 方法覆盖率 (Method Coverage)
- **JaCoCo工具**: Java代码覆盖率工具，Maven/Gradle插件
- **质量门禁策略**: 设定最低覆盖率阈值（如60%），未达标则构建失败
- **测试分层**:
  - 快速测试（核心功能，<1分钟）- Pre-commit
  - 完整测试（所有用例，2-5分钟）- Pre-push

#### 实践应用
```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <configuration>
        <rules>
            <rule>
                <limits>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.60</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</plugin>
```

#### 面试回答模板
> "我为项目建立了分层测试和质量门禁体系：
> 1. **快速测试套件** - 只运行核心测试（RAG评估、复杂度框架），30秒内完成，用于Pre-commit
> 2. **完整测试套件** - 运行所有测试用例，2-3分钟完成，用于Pre-push
> 3. **代码覆盖率监控** - 集成JaCoCo，设定60%最低覆盖率阈值
> 
> 这种分层策略平衡了**开发效率**和**代码质量** - 开发者提交时只需等待30秒，但推送前会进行完整验证，确保不会将问题代码推送到远程仓库。"

### 5. 权限管理与安全沙箱

#### 知识点
- **最小权限原则**: 只授予必要的操作权限
- **权限配置策略**:
  - `allow` - 白名单，明确允许的操作
  - `deny` - 黑名单，明确禁止的操作
- **危险命令识别**:
  - `rm -rf *` - 递归删除
  - `git push --force` - 强制推送（覆盖他人代码）
- **权限粒度**: 工具级（Bash、Read、Write）+ 参数级（通配符匹配）

#### 实践应用
```json
{
  "permissions": {
    "allow": [
      "Bash(./mvnw *)",
      "Bash(git status)",
      "Read(*)",
      "Grep(*)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)"
    ]
  }
}
```

#### 面试回答模板
> "我为项目配置了细粒度的权限管理体系：
> 1. **白名单策略** - 明确允许Maven、Git只读操作、文件读取等安全操作
> 2. **黑名单拦截** - 禁止递归删除、强制推送等危险操作
> 3. **审计日志** - 通过Pre-bash hook记录所有命令执行
> 
> 这套机制的设计理念是**纵深防御** - 即使AI助手或开发者误操作，也会被权限系统拦截。实际应用中，这避免了多次潜在的数据丢失风险。"

### 6. 持续集成与自动化测试

#### 知识点
- **CI/CD概念**: 持续集成（Continuous Integration）、持续部署（Continuous Deployment）
- **测试金字塔**:
  - 单元测试（最多，最快）
  - 集成测试（中等）
  - E2E测试（最少，最慢）
- **测试自动化价值**:
  - 快速反馈（秒级发现问题）
  - 回归保护（防止新代码破坏旧功能）
  - 文档作用（测试即规格说明）

#### 实践应用
```bash
# 快速测试套件
./mvnw test -Dtest=RAGEvaluationTest,ComplexityFrameworkTest -q

./mvnw test
```

#### 面试回答模板

> 1. **30个RAG评估测试** - 覆盖差旅政策查询、否定查询等场景，准确率80%
> 2. **5个复杂度框架测试** - 验证工具调用率100%
> 3. **性能压力测试** - 监控平均延迟、吞吐量等指标
> 
> 测试自动化的核心价值在于**快速反馈循环** - 开发者在提交前30秒内就能发现问题，而不是等到代码合并后才发现。这将问题修复成本降低了10倍以上（根据业界研究，越晚发现问题，修复成本越高）。"

### 7. 项目工程化成熟度评估

#### 知识点
- **Harness Audit框架**: 7个维度评估项目工程化水平
  1. 工具覆盖 (Tool Coverage)
  2. 上下文效率 (Context Efficiency)
  3. 质量门禁 (Quality Gates)
  4. 记忆持久化 (Memory Persistence)
  5. 评估覆盖 (Eval Coverage)
  6. 安全防护 (Security Guardrails)
  7. 成本效率 (Cost Efficiency)
- **评分标准**: 每个维度0-10分，总分70分
- **改进优先级**: 根据当前短板和投入产出比确定

#### 实践应用
```bash
# 运行Harness审计
/harness-audit

# 输出示例
Harness Audit (repo): 52/70
- Tool Coverage: 7/10
- Context Efficiency: 8/10
- Quality Gates: 6/10 ← 优先改进
- Security Guardrails: 5/10 ← 优先改进
```

#### 面试回答模板
> "我使用Harness Audit框架对项目进行了系统化评估和改进：
> 1. **初始评估** - 识别出质量门禁（6/10）和安全防护（5/10）是主要短板
> 2. **分阶段改进** - 
>    - 阶段1: 安全防护 +3分
>    - 阶段2: 上下文效率 +2分
>    - 阶段3: 质量门禁 +4分
> 3. **最终成果** - 总分从52/70提升至65/70，提升25%
> 
> 这个过程让我深刻理解了**工程化不是一蹴而就的** - 需要系统化评估、优先级排序、分阶段实施。Harness框架提供了可量化的指标，让改进效果可衡量、可追踪。"

### Q4: 你对代码覆盖率的理解是什么？

**回答框架**:
1. **定义** - 什么是代码覆盖率
2. **价值** - 为什么要关注覆盖率
3. **局限性** - 覆盖率不是万能的
4. **实践** - 如何合理使用

**示例回答**:
> "代码覆盖率是指测试用例执行时覆盖的代码行数占总代码行数的比例。它是衡量测试完整性的一个重要指标。
> 
> 覆盖率的价值在于：
> 1. **发现测试盲区** - 低覆盖率的模块可能缺少测试
> 2. **回归保护** - 高覆盖率意味着代码变更更容易被测试发现
> 3. **质量信号** - 覆盖率是团队对质量重视程度的体现
> 
> 但覆盖率也有局限性：
> 1. **高覆盖率≠高质量** - 可能只是执行了代码，但没有验证正确性
> 2. **不能盲目追求100%** - 有些代码（如异常处理）很难覆盖，性价比低
> 
> 我的实践是：设定60%的最低覆盖率阈值，重点关注核心业务逻辑（RAG、复杂度评估、任务分解）的覆盖率，而不是追求全局100%。"

## 💡 关键技术术语

### Git相关
- **Staging Area (暂存区)**: `git add` 后文件存放的区域
- **Git Hooks**: Git事件触发的脚本
- **Pre-commit**: 提交前执行的hook
- **Pre-push**: 推送前执行的hook

### 测试相关
- **Code Coverage (代码覆盖率)**: 测试覆盖的代码比例
- **JaCoCo**: Java代码覆盖率工具
- **Unit Test (单元测试)**: 测试单个函数/类
- **Integration Test (集成测试)**: 测试模块间交互
- **Regression Test (回归测试)**: 验证新代码不破坏旧功能

### 安全相关
- **Secret Scanning (敏感信息扫描)**: 检测代码中的密钥、密码
- **Least Privilege (最小权限原则)**: 只授予必要权限
- **Whitelist (白名单)**: 明确允许的操作列表
- **Blacklist (黑名单)**: 明确禁止的操作列表

### 工程化相关
- **CI/CD**: 持续集成/持续部署
- **Quality Gate (质量门禁)**: 代码质量检查点
- **Harness Audit**: 工程化成熟度评估框架
- **Context Efficiency (上下文效率)**: 理解项目所需的时间/成本

## 🎯 面试准备清单

- [ ] 能清晰描述3个阶段的改进内容
- [ ] 能解释每个改进的技术原理
- [ ] 能说出量化的改进效果（分数、百分比）
- [ ] 能回答"为什么这样做"（不只是"做了什么"）
- [ ] 准备1-2个具体的问题案例（如拦截了哪次泄露）
- [ ] 了解相关技术术语的英文表达
- [ ] 能画出架构图/流程图（如果面试官要求）

---

**最后提醒**: 面试时不要只说"我做了X"，要说"我为了解决Y问题，做了X，达到了Z效果"。展示你的**思考过程**和**问题解决能力**，而不只是技术实现。
