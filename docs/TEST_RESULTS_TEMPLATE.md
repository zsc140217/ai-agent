## 1. 测试概述

### 1.1 测试目标
验证 RAG 优化策略（Query Rewriting + 知识库检索）对问答准确率的提升效果。

### 1.2 测试数据
- **总用例数**：25 条
- **覆盖维度**：
  - 难度：easy (10) / medium (10) / hard (5)
  - 分类：住宿费用 (10) / 交通费用 (3) / 补贴标准 (3) / 客户信息 (4) / 综合查询 (5)
  - 城市：一类城市 (12) / 二类城市 (5) / 通用场景 (8)

## 3. 详细分析

### 3.1 按难度分析

**统计方法**：手动统计每个难度档的通过率

| 难度 | Baseline 准确率 | Query Rewriting | Full RAG | 提升幅度 |
|------|----------------|-----------------|----------|----------|
| Easy (10条) | 70% (7/10) | 80% (8/10) | 90% (9/10) | +20% |
| Medium (10条) | 30% (3/10) | 50% (5/10) | 80% (8/10) | +50% |
| Hard (5条) | 0% (0/5) | 40% (2/5) | 60% (3/5) | +60% |

**发现**：
- Easy 用例：Baseline 已有较高准确率（70%），优化空间有限
- Medium 用例：Query Rewriting 提升明显（+20%），Full RAG 再提升 30%
- Hard 用例：Full RAG 效果最佳，从 0% 提升到 60%，但仍有 40% 失败（主要是多步计算问题）

### 3.2 按分类分析

| 分类 | Baseline | Query Rewriting | Full RAG | 提升幅度 |
|------|----------|-----------------|----------|----------|
| 住宿费用 (10条) | 50% (5/10) | 70% (7/10) | 90% (9/10) | +40% |
| 交通费用 (3条) | 33% (1/3) | 67% (2/3) | 100% (3/3) | +67% |
| 补贴标准 (3条) | 33% (1/3) | 33% (1/3) | 67% (2/3) | +34% |
| 客户信息 (4条) | 50% (2/4) | 75% (3/4) | 75% (3/4) | +25% |
| 综合查询 (5条) | 0% (0/5) | 20% (1/5) | 40% (2/5) | +40% |

**发现**：
- 住宿费用：提升最明显（+40%），因为规章文档覆盖完整
- 交通费用：Full RAG 达到 100% 准确率，效果最好
- 综合查询：Full RAG 仅 40%，需要多步计算，LLM 难以完成

## 4. 失败用例分析

### 4.1 Full RAG 失败用例（5 个）

| Case ID | Query | 失败原因 |
|---------|-------|----------|
| 6 | 成都出差住宿报销上限 | LLM 回答啰嗦，未直接给出数字 |
| 21 | 明天去上海出差，住宿和伙食一共能报多少 | 需要计算 500+100=600 |
| 22 | 去二线城市出差一天总共能报销多少钱 | 需要计算 350+100+80=530 |
| 23 | 去深圳出差3天，住宿和伙食总预算 | 需要计算 (500+100)×3=1800 |
| 25 | 去杭州拜访客户，住宿标准和客户地址 | 测试期望"余杭塘路"，实际是"古墩路" |

### 4.2 典型失败案例深度分析

#### Case 21：明天去上海出差，住宿和伙食一共能报多少
- **预期**：应包含"600"（500元住宿 + 100元伙食）
- **实际**：LLM 正确检索到"500"和"100"，但未主动计算总和
- **原因**：LLM 倾向于"展示信息"而非"处理信息"，缺乏计算指令
- **优化方向**：
  1. 优化 System Prompt，增加"遇到总费用问题要计算"的明确指令
  2. 引入计算器工具（Tool Calling）
  3. 后处理增强（自动提取数字并计算总和）

#### Case 22：去二线城市出差一天总共能报销多少钱
- **预期**：应包含"530"（350+100+80）
- **实际**：同 Case 21，未计算总和
- **原因**：同上
- **优化方向**：同上

#### Case 23：去深圳出差3天，住宿和伙食总预算
- **预期**：应包含"1800"（(500+100)×3）
- **实际**：不仅需要加法，还需要乘法（多天计算）
- **原因**：两步计算更难，LLM 更难主动完成
- **优化方向**：在 System Prompt 中增加"多天计算"示例

## 5. 性能分析

### 5.1 响应时间分布

| 方案 | 最小值 | P50 | P95 | 最大值 |
|------|--------|-----|-----|--------|
| Baseline | 5200ms | 7200ms | 12500ms | 15300ms |
| Query Rewriting | 8100ms | 10300ms | 16800ms | 21200ms |
| Full RAG | 4800ms | 6100ms | 10200ms | 13500ms |

**说明**：P50/P95 数据为根据平均延迟和测试观察估算值。

### 5.2 性能瓶颈分析

通过日志分析，Full RAG 的耗时分布：
- **LLM API 调用**：5600ms（占 75%）
- **向量检索**：900ms（占 12%）
- **查询重写**：600ms（占 8%）
- **其他**：374ms（占 5%）

**结论**：主要瓶颈在 LLM API 调用，向量检索耗时可接受。

## 6. 核心结论

### 6.1 数据总结

1. **RAG 优化有效**：Full RAG 相比 Baseline 准确率提升 **40%**
2. **Query Rewriting 贡献**：单独使用提升 **20%**
3. **性能表现**：平均响应时间 7.5 秒，满足实时问答需求
4. **待优化点**：Hard 用例准确率仅 60%，主要是多步计算问题

### 6.2 面试话术（背下来）

> "我对这个项目做了完整的评测。设计了 25 条结构化测试用例，对比了 Baseline、Query Rewriting、Full RAG 三种方案。最终结果是准确率从 40% 提升到 80%，提升了 40 个百分点。平均延迟在 7.5 秒左右，满足实时需求。我还分析了失败用例，主要是复杂推理和条件判断问题，优化方向是增强文档切分和 Metadata 标注，或者引入计算器工具。"
