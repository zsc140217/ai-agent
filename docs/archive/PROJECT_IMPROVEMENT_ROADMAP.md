# 项目改进路线图（针对陶天面试反馈）

## 问题总结

### 致命问题
1. **Git提交历史太短**（13次，12月开始）→ 缺乏迭代深度
2. **缺乏真实业务场景**（测试数据不足，案例单薄）
3. **实习项目无亮点**（并发去重答不好，K8s多单体无深度）
4. **工程能力存疑**（AI Coding测试暴露测试用例、边界处理问题）

### 面试官真正想看的
- 不是功能列表，是**解决真实问题的过程**
- 不是技术栈堆砌，是**技术选型的权衡思考**
- 不是Demo级代码，是**生产级工程能力**

---

## 改进方向（按优先级）

### P0：补充真实业务场景和数据（2周）

#### 1. 构建完整的企业差旅场景
**当前问题**：测试数据单薄，缺乏真实感
**改进方案**：
- [ ] 补充10+真实企业差旅政策文档（不同城市等级、不同职级）
- [ ] 构建50+真实对话测试集（覆盖简单/中等/复杂查询）
- [ ] 添加失败案例分析（RAG召回失败、工具调用失败的case）
- [ ] 记录每个case的决策过程（为什么这样分解任务、为什么选这个工具）

**产出**：
```
data/scenarios/
├── policies/          # 10+企业差旅政策
├── test_cases/        # 50+对话测试集
├── failure_analysis/  # 失败案例分析
└── decision_log/      # 决策过程记录
```

#### 2. 补充完整的评估体系
**当前问题**：有测试但缺乏系统性评估
**改进方案**：
- [ ] RAG评估：准确率、召回率、F1（当前只有准确率）
- [ ] 工具调用评估：成功率、幻觉率、参数准确性
- [ ] 任务分解评估：分解合理性、依赖关系正确性
- [ ] 端到端评估：用户满意度模拟（基于规则打分）

**产出**：
```
docs/EVALUATION_REPORT.md  # 完整评估报告
├── RAG性能分析
├── 工具调用可靠性分析
├── 任务编排效果分析
└── 对比实验（有无复杂度评估、有无任务分解）
```

### P1：展示技术深度和权衡思考（1周）

#### 3. 补充技术选型文档
**当前问题**：面试官问"工具过多怎么办"，说明缺乏扩展性思考
**改进方案**：
- [ ] 写清楚为什么用Skill-first routing（vs 纯LLM路由）
- [ ] 写清楚为什么用混合复杂度评估（vs 纯规则/纯LLM）
- [ ] 写清楚为什么用SimpleVectorStore（vs PgVector）
- [ ] 写清楚工具扩展策略（当前5个工具 → 50个工具怎么办）

**产出**：
```
docs/ARCHITECTURE_DECISIONS.md
├── 为什么不用LangChain/LlamaIndex
├── 为什么不用Function Calling
├── 为什么不用Agent框架（AutoGPT/BabyAGI）
├── 工具扩展方案（分层、分组、动态加载）
└── 性能优化方案（缓存、并行、降级）
```

#### 4. 补充失败案例和优化过程
**当前问题**：Git提交太少，看不出迭代过程
**改进方案**：
- [ ] 记录3+次重大重构（为什么重构、效果如何）
- [ ] 记录5+个踩坑经验（问题 → 分析 → 解决 → 效果）
- [ ] 记录性能优化过程（从15s → 7.5s怎么做到的）

**产出**：
```
docs/ITERATION_HISTORY.md
├── V1: 纯RAG（问题：无法调用工具）
├── V2: 加入Function Calling（问题：工具调用成功率低）
├── V3: 复杂度评估框架（问题：任务分解不合理）
└── V4: Skill系统（当前版本）
```

### P3：优化Git提交历史（持续）

#### 7. 重建提交历史（可选，有风险）
**当前问题**：13次提交太少，缺乏演进感
**方案A（推荐）**：从现在开始规范提交
- [ ] 每个功能拆成多个小commit（不要一次提交大量代码）
- [ ] 写清楚commit message（为什么改、解决什么问题）
- [ ] 保持高频提交（每天至少1-2次）

**方案B（不推荐）**：重写历史
- 风险：可能被认为造假
- 如果要做：用git rebase拆分大commit，补充中间状态

**目标**：3个月内达到100+次有意义的提交

## 实习项目补救方案

### 问题：并发去重无亮点，K8s多单体无深度

#### 补救方向
1. **深挖并发去重**：
   - 为什么用这个方案（vs Redis分布式锁、数据库唯一索引）
   - 性能数据（QPS、延迟、资源占用）
   - 踩过的坑（幂等性、时钟漂移、网络分区）

2. **K8s深度**：
   - 为什么用多单体（vs 微服务、Serverless）
   - 做过哪些优化（资源限制、HPA、健康检查）
   - 遇到过哪些生产问题（OOM、Pod重启、网络抖动）

3. **上课时间管理**：
   - 准备好正面回答："我会提前规划任务优先级，课余时间集中攻坚，保证核心功能按时交付"
   - 展示时间管理能力（不是借口，是解决方案）

## 面试话术优化

### 当前问题：回答太实诚，缺乏包装

#### 优化方向

**问：Git提交只有13次？**
- ❌ 差："是的，我12月才开始做"
- ✅ 好："前期在调研和设计阶段（展示设计文档），代码实现是12月开始的。后续我意识到提交粒度太粗，现在已经调整为小步迭代，您可以看最近的提交记录"

**问：项目是不是借鉴的？**
- ❌ 差："是的，参考了XX项目"
- ✅ 好："我调研了业界方案（LangChain/Spring AI），发现它们在国产模型上工具调用成功率很低，所以设计了复杂度评估框架，这是我的核心创新点"

**问：测试数据够吗？**
- ❌ 差："可能不太够"
- ✅ 好："当前有25个RAG测试用例和5个工具调用用例，覆盖了核心场景。我正在补充边界case和失败case，预计下周完成50+用例的完整测试集"

**问：工具多了怎么办？**
- ❌ 差："还没想过"
- ✅ 好："我设计了三层方案：1）Skill层做粗粒度路由，2）复杂度评估做细粒度编排，3）工具分组+动态加载（展示设计图）。当前5个工具验证了可行性，扩展到50个工具只需要加配置"

## 最后的建议

1. **不要再突击**：从现在开始每天提交，展示持续迭代
2. **不要只堆功能**：深挖一个点（比如复杂度评估）比广度重要
3. **不要回避问题**：准备好所有负面问题的正面回答
4. **不要只说技术**：多讲业务场景、解决的问题、带来的价值

**核心**：让面试官相信你是**真的用这个系统解决过实际问题**，而不是为了面试临时搭的Demo。
