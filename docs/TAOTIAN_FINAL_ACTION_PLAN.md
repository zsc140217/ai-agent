## 实习项目补救方案

### 问题：并发去重无亮点，K8s多单体无深度

#### 补救方向1：深挖并发去重

**准备话术**：
```
【技术选型】
- 方案对比：Redis分布式锁 vs 数据库唯一索引 vs ZooKeeper
- 为什么选Redis：性能高（QPS 5000+）、部署简单、团队熟悉
- 为什么加数据库兜底：Redis故障时保证数据一致性

【性能数据】
- QPS：5000+（单机Redis）
- 延迟：P95 < 50ms
- 资源占用：Redis内存 < 100MB

【踩过的坑】
1. 时钟漂移导致锁提前释放
   - 问题：分布式环境下不同机器时钟不同步
   - 解决：改用Redisson的看门狗机制（自动续期）
   
2. 网络分区导致脑裂
   - 问题：Redis主从切换时，旧主还持有锁
   - 解决：使用RedLock算法（多个Redis实例）
   
3. 幂等性问题
   - 问题：重试时可能重复执行
   - 解决：业务层加幂等性校验（唯一ID）
```

#### 补救方向2：K8s深度

**准备话术**：
```
【为什么用多单体】
- 业务特点：各服务独立，无强依赖
- 团队现状：微服务治理成本高，团队规模小
- 技术选型：单体 + K8s 水平扩展，兼顾简单和性能

【做过哪些优化】
1. 资源限制：requests/limits 设置（防止OOM）
2. 健康检查：liveness/readiness probe（自动重启）
3. HPA：基于CPU/内存自动扩缩容
4. 滚动更新：零停机部署

【遇到过哪些生产问题】
1. Pod频繁重启
   - 问题：内存泄漏导致OOM
   - 排查：kubectl logs + jmap dump
   - 解决：修复代码 + 调整内存限制
   
2. 网络抖动
   - 问题：偶发性请求超时
   - 排查：Prometheus监控 + 网络抓包
   - 解决：增加重试机制 + 调整超时时间
```
